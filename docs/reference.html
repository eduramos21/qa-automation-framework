Reference

The config schema, how to add a stack, and what every agent and skill does. If you are looking for what this is and why, start at the overview.

qa.config.yml

One file at the project root. Every agent reads it before doing anything, so a wrong value here makes everything downstream confidently wrong.

stacks.mobile.platforms[android, ios]

policies.forbid

Five rules are understood out of the box, and qa-policy checks all five. Anything else you put in the list is read by the agents but not machine checked.

RuleCatchesCheck
hard_sleepswaitForTimeout, time.sleep, Thread.sleep, implicitly_wait, driver.pause, cy.wait(500)exact
absolute_xpath//div[3]/span, anything rooted at /htmlexact
conditional_assertionsAn assertion inside a branch, so the test can pass by skipping its own checkheuristic
no_assertionA test that drives the app and never checks anythingheuristic
shared_mutable_statedescribe.serial, module level mutables, enforced orderingheuristic
The heuristics label themselves in the output. They are meant to catch the obvious case fast, inside an edit hook, before it lands. Anything subtler is the auditor's job, and it has a model to reason with.

Profiles

A profile teaches the agents one stack. It holds no QA reasoning, just the mechanics.

profiles/<name>/
  profile.yaml      commands, layout, templates, selector priority
  CONVENTIONS.md    how to write a test here, with real code
  templates/        skeleton files the author agent copies
  ci/               one pipeline file per CI provider

Adding one

cp -r profiles/_template profiles/java-selenium-junit5
# fill in profile.yaml, name must match the folder
# write CONVENTIONS.md with real code, this is the file that decides
# whether generated tests look like they belong in your repo
python3 scripts/validate_profiles.py

Then point a project at it with stacks.web.profile: java-selenium-junit5. No agent changes.

Java plus Selenium plus JUnit 5 is deliberately not shipped. It is the obvious next profile and writing it from the template is the fastest way to find out whether this design holds up.

Agents

Three. An agent exists where the work reads a lot of files and needs no conversation. Everything interactive is a skill running in the main thread, because a subagent cannot ask you a question.

test-author

Writes tests and page objects in the active profile's style. Runs what it wrote, then breaks it on purpose to confirm it can fail. Reports which design rows it did not write and why.

test-maintainer

Fixes failing and flaky tests and refactors duplication. Triages through five causes before editing. Fixes the cause once rather than the symptom four times.

suite-auditor

Scores a suite against a nine area rubric with evidence, ranks findings by cost over effort, and changes nothing.

What they refuse to do

  • Author: promote a unit row to e2e because e2e is the layer it can reach. Invent an expected result. Write a row the design said not to automate.
  • Maintainer: add a sleep, widen an assertion to make it pass, add retries to hide a flake, or delete a test to clear a red build.
  • Auditor: change anything, publish a total score, or report a finding without a path and a line behind it.

Those lists are the interesting part of each agent. The rest is method.

Reference skills

Model invoked, pulled in by the workflows and usable on their own.

SkillHolds
qa-configHow to resolve the project setup and what to do when it fails. Every other skill leans on this
test-design-techniquesEquivalence partitioning, boundary values, decision tables, state transitions, pairwise. Which technique for which shape of requirement, risk scoring, and choosing a layer
flake-triageThe five causes of a red test in the order they are actually likely, and the rerun protocol that tells a flake from a defect
bug-reportA report shape that avoids the round trip, and how to file to the configured tracker
There is no page-object-authoring skill. That knowledge lives in each profile's CONVENTIONS.md, where it can be stack specific and correct, instead of in a skill where it would have to be generic and vague.

Tools and wiring

Two commands

Both stdlib only Python, because they run on the critical path of every task and adding a pip install there would be a bad trade for a few fields of YAML.

qa-context [stack] [--paths]     resolve config + active profile + conventions
qa-policy  <file>... | --stack   check against policies.forbid

One hook

PostToolUse on Write and Edit runs qa-policy --hook. A test written with a forbidden pattern in it exits 2, which is the code that sends the message back to be fixed rather than only printing it. Outside a project with a config, it does nothing.

Checks

python3 scripts/validate_profiles.py   every profile.yaml and every qa.config.yml
python3 scripts/test_qa_context.py     the config parsing
python3 scripts/test_qa_policy.py      that qa-policy fires on what it claims to

All three run in CI, along with both web demo suites against the live site and a typecheck of the mobile example.

The third one matters most. A policy checker that never fires reads as coverage and is worse than not having one, so its checks include the shapes it must catch and the shapes it must stay quiet on.
